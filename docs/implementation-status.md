# QNX-Quiver implementation status

Updated 25 November 2026. Source completion, compile checks, host tests, and guest runtime evidence are listed separately; a successful build is not treated as guest verification.

## Implemented in source

- BAR2 protocol v3 and client API v3 preserve the ring offsets while adding snapshot generations and CAN, IMU, and actuator telemetry. Multi-client readers have explicit serialized work-sharing semantics.
- The QNX PCI resource manager owns BAR2, keeps it private, validates the protocol, withdraws `/dev/quiver` on PCI-server/device loss, and reacquires after recovery. Read-only calls may reopen and revalidate a recovered service; state-changing ring requests are never replayed after ambiguous disconnects.
- CAN FD DDK code maps extended identifiers and legal lengths through the rings. TX retries ring-full errors for a bounded 5 ms, RX queue overflow discards the oldest frame, both losses are counted, and bus-off/recovery state is exposed with a transition generation.
- Host snapshots use a bounded retry. The host simulator validates CAN format, rejects unsafe actuator commands, acknowledges accepted/rejected command IDs, expires outputs to zero, counts IMU ring drops, and reports measured rate, wake-lateness percentiles, and missed deadlines. QNX CAN, IMU, and actuator drop counters are exported through the same snapshot API.
- QNX utilities consume timestamped IMU data and detect non-advancing source timestamps, publish bounded actuator commands and wait for acknowledgement, capture fault/counter traces, and provide a controller demonstration that emits zero after a stale-sample timeout.
- A development supervisor starts the PCI manager before the CAN, IMU, and trace processes, restarts failed children with capped backoff, and coordinates shutdown. Children inherit its process type, so this supervisor is not a production least-privilege launcher.
- The PCI manager uses a periodic QNX timer pulse to run health/recovery checks even when no client request is arriving. It detects changes to `/dev/pci/server_id_1`, withdraws the public node, releases BAR2, and re-executes itself to rebuild libpci state against the new server instance. The supervisor chooses a writable trace destination (`/tmp` or `/dev/shmem`) instead of assuming `/tmp` exists as a writable directory.
- The WSL launcher can place ivshmem behind a PCI bridge. A QMP script requires `DEVICE_DELETED`, checks device removal/reinsert in `query-pci`, and a QNX helper waits for `/dev/quiver` withdrawal/reacquisition.
- The security policy fragment now declares process types for the added services and compiles as a fragment. It is not the guest's active policy.

## Additional verification on 25 November 2026

- `make -B all` passed with the installed QNX SDP 8.0 x86_64 toolchain and warnings as errors before this recovery change; the updated PCI manager and supervisor both compile with the same flags. The host unit suite passes 13 tests, and the simulator self-test passes.
- A disposable full-service IFS built with `qemu/build_hotplug_test_ifs.ps1 -IncludeServices` boots in snapshot mode. The resident manager validates BAR2 and QVB1 v3; the client probe reads protocol geometry and counters; the PCI database probe confirms the manager's exclusive attach.
- Guest CAN FD loopback passed with extended ID `0x1abcde` and 64 data bytes preserved. Injected CAN bus-off appeared in the DDK status as `bus-off`, generation 1; clearing the fault returned `active`, generation 2. The unconsumed RX path advanced the QNX drop counter, exercising oldest-drop accounting under load.
- The guest IMU client consumed advancing timestamped samples. A valid actuator command was acknowledged; an out-of-range command was rejected locally; a later fault snapshot showed the host output returned to zero after TTL expiry. Trace capture produced 10 rows plus its CSV header. With `IMU_STUCK` injected, the controller reported stale input and sent the safe zero command.
- A corrected root-bus test derived the ACPI eject bit from QMP PCI inventory. With the host-injected eject acknowledgment, QEMU emitted removal and the QNX manager withdrew `/dev/quiver` after `PCI_ERR_ENOTSUP`. Reinsertion enumerated in QEMU but BAR0/BAR2 stayed unassigned; the harness reported `UNVERIFIED`. This still does not prove native QNX eject acknowledgment or successful reinsert recovery.
- A controlled PCI-only Q35 + PCIe-to-PCI-bridge experiment isolated live insertion failure from Quiver: PCI logs report link-event notifications unsupported; after QMP insertion, QNX does not add ivshmem to its PCI database or assign BARs. With the device already present, restarting `pci-server` makes QNX enumerate it and assign BAR0/BAR2. In the v3 guest, the resident manager detected the changed `/dev/pci/server_id_1` identity, withdrew `/dev/quiver`, re-executed itself, and republished the node; CAN RX/TX, IMU, and trace services returned online and the client probe passed.
- The first supervisor guest run exposed repeated CAN child launches: QNX returned a child wait status while the associated DDK process still existed. The supervisor now verifies process disappearance before restarting or forgetting a PID, preserves exponential backoff until a child has run stably, and waits for process exit during shutdown. A guest run held two CAN endpoints stable, restarted a killed trace child, and stopped all supervised children on SIGTERM.
- A deliberate PCI-manager process termination withdrew `/dev/quiver`. The supervisor stopped dependent clients, restarted the manager, waited for `/dev/quiver` to return, and launched fresh CAN RX/TX, IMU, and trace processes; each reported online. Two fresh QEMU cold boots also reached manager and service readiness. PCI-server stop/restart recovery now also passes in the current v3 guest as described above.

## Verified on the development host

- The policy-enabled IFS path now accepts a complete target policy source, merges the Quiver rules and an image-type-specific PCI-server channel permission, embeds `/proc/boot/secpol.bin`, pushes it before persistent startup, and launches the PCI server and Quiver manager under explicit types. It also packages positive and negative client probes (`quiver-client-probe`, `quiver-client-denied-probe`) and supports `-SecpolGenerate` for disposable `secpolgenerate` observation builds.
- Q35 `pcie-root-port` diagnostic (QEMU 10.2.1, `QNX_PCI_TOPOLOGY=pcie-root-port`, `build/ifs-pci-only-diag.bin` SHA256 `97330FE9CD3314833B32F99FF534D1967DAFFD680FB516C772425AA3CAE979C0`): With `PCI_BASE_VERBOSITY=5 pci-server -vv`, `pci_server-buscfg-hotplug.so`, and `pci_server-event_handler.so`, `pci-server` v3.2 enumerated `B1:D0:F0` (`1af4:1110`, BAR0 `0x41700000`, BAR2 `0x4140000c`), logged `initialize_slot_event_notifications()` and `_cap_msix_get_nirq()` on the `pcie-root-port` (`B0:D2:F0`), and then terminated before publishing `/dev/pci/server_id_1`. `quiver-pci-db-probe` confirmed `B1:D0:F0` in `/dev/shmem/pci/pci_db` with `PCI_ERR_SERVER_NOT_AVAILABLE`. Native PCI hot-unplug/reinsert remains unsupported by QNX SDP 8.0 `pci-server` on QEMU 10.2.1 across all tested topologies; `pci-server` restart recovery (`quiver-pci-rm` self-re-exec on `/dev/pci/server_id_1` identity change) is retained as the verified software recovery path.
- Active security policy guest verification (QEMU 10.2.1, `QNX_PCI_TOPOLOGY=pci-bridge-hotplug`, `build/ifs-quiver-policy-test.bin` SHA256 `7D2BEC7FEA1D22309999DBA16E077F8AAAC8331A77F90C91F49AD3896B7A510F` and `build/ifs-quiver-supervisor-policy.bin` SHA256 `D9AE8430C875566BC6EA8E71D13079DC63D3B74153746F4083390EF70CCE1DF3`): Derived `qnx/security/qemu_target_base.policy` from `secpolgenerate -N -u -f 1` on a disposable observation image (`build/ifs-secpol-gen.bin`), merged `qnx/security/qnx_quiver.policy` (updated with `mem_phys` for `quiver_pci_t` and `quiver_supervisor_t` with `settypeid` subranges), compiled immutable `secpol.bin`, and booted in snapshot mode. `secpol -Q` reported `immutable`; `pidin -f a_n` confirmed `pci-server` running as `pci_server_t`, `quiver-supervisor` as `quiver_supervisor_t`, and supervisor-spawned children under their distinct least-privilege types (`quiver_pci_t`, `quiver_can_t`, `quiver_imu_t`, `quiver_trace_t`) via `secpol_posix_spawnattr_settypeid()`. - `build/ifs-quiver-services.bin` (SHA256 `5C280F23A318194C0B9407B5DB93A898BECD6DD8F49E47AAD6232450A2000DA8`) also booted on `pci-bridge-hotplug` in QEMU 10.2.1, with `quiver-pci-db-probe` confirming exclusive attach at `B1:D0:F0` and `quiver-client-probe` passing.
- `make -B all` passed with QNX SDP 8.0 x86_64 (`-Wall -Wextra -Werror`), all 13 Python unit tests passed (`py -3 -m unittest discover -s tests -v`), and `py -3 host/sim_engine/quiver_sim.py --self-test` passed after the final policy and builder edits.

- QNX SDP 8.0 x86_64 `make -B all` completes with `-Wall -Wextra -Werror`, including all service and supervisor binaries and the policy fragment. (`make host-test` cannot be used directly in this Windows shell because `python3` is not on PATH; the equivalent unit suite was run with `py -3`.)
- Thirteen Python unit tests pass. They cover v3 initialization, invalid mapping/version rejection, serialized multi-reader work sharing, QNX drop metrics, stalled snapshot timeout, CAN-FD validation and bus-off hold/recovery, IMU-stuck timestamps, actuator safety/acknowledgement/expiry, simulator operation, and PCI slot inventory lookup.
- Two-second Windows timing runs at a 1 kHz target measured about 998.5–999.0 Hz without injected delay (p95 wake lateness about 612–648 microseconds, 2–3 misses per second). With a repeated 500 microsecond delay, the run measured about 877–878 Hz and about 856–862 missed deadlines per second. Treat these as host characterization only; no hard real-time threshold is claimed.
- The bridged WSL QEMU 10.2.1 guest boots and `query-pci` shows ivshmem behind `quiver_bridge` on bus 1 with BAR0 256 bytes and BAR2 4 MiB.
- The default-configuration guest returned successfully from QMP `device_del` but produced no `DEVICE_DELETED` event; `query-pci` still listed `quiver_ivshmem`.
- A full test IFS with both QNX 8.0 modules and `DO_BUS_CONFIG=yes` was built. On i440fx root bus, initial ivshmem BAR0/BAR2 were assigned. QMP `device_del` required a host-injected write to the ACPI eject register (HMP `o /w 0xae08 0x10`) before QEMU emitted `DEVICE_DELETED` and removed the function from `query-pci`; the QNX manager withdrew `/dev/quiver` in the earlier watcher run. This proves guest removal recovery only after a host-forced ACPI acknowledgment, not QNX event-handler processing.
- Reinsert with QMP `device_add` on the same root-bus slot restored the device in `query-pci` but left BAR0 and BAR2 at address `-1`, even with the hotplug bus-configuration module enabled. The manager correctly stayed offline because BAR2 could not be read/mapped. The updated `tests/qemu_pci_hotplug.py` detects and reports this as `UNVERIFIED` rather than counting QEMU enumeration as a complete recovery. QEMU 10.2.1 also asserts if an ivshmem memory-backend object is reused for a second attachment; use a fresh backend object ID for each reinsert while mapping the same shared file.
- The alternate QNX `pci_server-buscfg2-hotplug.so` module is present in SDP 8.0 and is now selectable with `qemu/build_hotplug_test_ifs.ps1 -Buscfg2`; the builder successfully creates and inspects an IFS that selects it. Running that image on Q35 with an empty PCIe root port still faults the supplied PCI server at startup (`Memory fault`, then `/dev/pci/server_id_1` is unavailable). The Quiver manager stays resident and reports that it is waiting offline, but this profile cannot establish a live PCI inventory or prove native hotplug. The guest also lacks the EIDE device expected by its root filesystem in this Q35 topology, so it does not reach a usable system boot.
- With BAR2 initialized by the WSL host simulator, the standard hotplug IFS boots QNX on Q35 with a PCIe-to-PCI bridge and publishes `/dev/quiver` at BAR2 `0x41400000`. A bundled guest probe confirms `1af4:1110` at B1:D0:F0, expected BAR sizes (256 bytes and 4 MiB), and exclusive ownership by the resource manager.
- Native QMP `device_del` still does not remove ivshmem on that Q35 topology, even when the harness writes the ACPI eject register. Starting QNX with the bridge present but ivshmem absent correctly leaves the manager resident offline. QMP `device_add` shows the function in QEMU but leaves BAR0/BAR2 at `-1`; QNX's PCI database still omits it and `/dev/quiver` stays withdrawn. QNX `pci-tool` is included in the test IFS; for this ivshmem function its context help offers reset only, not virtual hotplug.
- The controlled insertion experiment separates the remaining lifecycle limitation from the service: QNX's PCI event path on the tested topology does not process ivshmem link insertion. A `pci-server` restart while the device is present re-enumerates it and assigns BARs; Quiver detects the PCI-server resource identity change and re-executes itself, after which the node, dependent services, trace file, and client API recover. This is a verified software recovery fallback, not native live hotplug.
- Actual guest-driven hot-unplug and a full live remove/reinsert acceptance cycle remain unverified. Host-injected ACPI eject acknowledgment can make QEMU remove the device, but that does not prove QNX initiated the eject; the previously tested reinsertion had unassigned BARs until PCI-server re-enumeration. QMP acceptance or QEMU-only enumeration is not a pass.

## Runtime gates and limits

- The v3 manager, client, CAN DDK, IMU, actuator, trace, controller, and supervisor startup/readiness/child-restart/shutdown flows now have disposable guest runtime evidence as recorded above. PCI-manager-process outage recovery, PCI-server identity-change recovery, and two cold starts passed. Native guest-visible PCI hot-unplug/reinsert remains open on the tested QEMU topology.
- The supplied guest has no active `/proc/boot/secpol.bin`. The exact PCI-server type/connect permission depends on the product image. Merge the fragment, identify the PCI-server type with `secpolmonitor`, assign per-service types, and test both permitted and denied operations before production.
- CAN-FD loopback, TX ring backpressure, blocked RX wake on resumed traffic (earlier guest build), bus-off/recovery status, and RX drop accounting have virtual guest evidence. This proves neither physical arbitration nor transceiver timing or electrical behavior.
- Timing output reports p50/p95/p99/max wake lateness, measured rate, and deadline misses. Results from the Python simulator on a general-purpose Windows/WSL host are characterization data, not a real-time acceptance guarantee.
- The verified target remains QNX SDP 8.0 x86_64. Other architectures and cache-coherency models are unsupported until separately specified and tested.
